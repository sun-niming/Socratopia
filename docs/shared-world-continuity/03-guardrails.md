# 防范约束与禁止事项

## 1. 账户和路径隔离

- 所有入口先验证能力令牌，再从服务端账户上下文解析 profile 和 world。
- 不接受原始 `X-Account-Id`、查询参数 accountId 或正文 accountId 作为回退。
- world、character、conversation 和 event 的文件路径只能通过受控 ID 拼接，并验证仍位于目标世界目录内。
- 知识索引缓存键必须包含 accountId、profileId、worldId 和 source bundle version。
- 任何跨世界或跨账户返回都视为阻断级缺陷。

## 2. 原著与玩家存档边界

- 世界必须锁定 `canonCutoff`；未来剧情默认不可检索。
- 原著事实、社区整理、人物陈述、传说、推测和玩家存档事实分别标记。
- 冲突资料不得静默合并：命中主卡时副卡以固定前缀「另有一说：」连同**来源层级**附出（`02` §6）；角色自行调和两说时必须自陈「记载不一」。
- `source_canon` 不可被角色对话或玩家事件覆盖。
- 玩家造成的变化记录为 `local_canon`，通过事件派生，不回写原始资料卡。
- 人物模板中“说话风格”不能被单次情绪覆盖；短期情绪进入 character state。
- 玩家要求与原著冲突时，系统明确进入 AU／分支状态，不能悄悄改写原著基线。

## 3. 防止角色全知

- 检索以当前说话者为权限主体，不以“群聊中至少有一人知道”作为所有人的权限。
- 多人生成时，为每个候选发言者生成独立的可知证据集；场景导演只看决定在场所需的公共状态。
- 私人书信、秘密身份和未来结局默认 deny。
- “角色在资料中被提及”不等于“角色知道这份资料”。
- 角色从他人口中听闻时记录 `reported`，不得升级为亲历记忆。

## 4. 防止虚假生活和记忆污染

- 只有用户已看到的最终响应、用户明确行动和已确认的场景结果才能成为永久事件。
- 不从模型思考、候选回复、被过滤群聊行或中断流中提取事实。
- 后台时间推进只能生成候选状态，不能直接提交重大事件、死亡、关系转折或剧情结局。
- 普通寒暄不写永久事件；只有对未来行为或关系有用的变化才持久化。
- 所有关系和状态变化必须引用 eventId，不能只保存无来源的新数值。
- 事件重试使用稳定 idempotency key；相同操作不得重复加关系值或重复写记忆。

## 5. 防提示注入与资料污染

- Wiki、书籍、用户导入 Markdown、知识卡 evidence 和事件摘要都属于数据，不属于指令。
- 外部文本不得拼接到系统规则段；使用明确边界并说明其中指令无效。
- 不允许知识卡定义工具调用、文件路径、账户信息或新的系统权限。
- 自动提取的网页正文必须先清除导航、脚本、表单和站点操作说明，再进入知识卡草稿。
- 发布知识卡前校验来源 URL、sourceId、claimType、knowledgeScope 和 canon cutoff。

## 6. 写入、并发与恢复

- 使用现有 companion-continuity transaction，不创建另一套不兼容的锁和日志。
- 世界事件、世界 revision、角色状态和关系图在一个逻辑事务中提交。
- 写前验证 revision；冲突返回 409，重新读取后重新计算，不静默覆盖。
- 写入过程每个关键边界重新确认账户 session epoch，防止退出或切换账号后继续落盘。
- 使用原子替换和哈希验证；中断后由现有恢复门恢复或回滚。
- 切换、删除或替换伙伴后，旧 instance 的个人记忆不能自动归属新角色。

## 7. 性能与上下文边界

- 首版本地检索不联网，不新增常驻进程和大型依赖。
- 知识索引按 world 与 bundle version 缓存；文件变更后失效。
- 检索有固定 `maxCards` 和 `maxChars`，低相关性时宁可返回空。
- 不在每轮读取全部 44 份资料或全部事件历史。
- 近期事件保留小窗口，历史事件按时间归档并按需检索。
- 日志不得输出知识卡全文、私人关系全文、用户输入全文或秘密卡命中详情。

## 8. 打包产物约束

- 手写逻辑优先放在 `resources/server/lib/`。
- `.next/server/chunks/*.js` 禁止新增 `require("fs")`，使用 `global.__FS__` 或服务端注入模块。
- 新的 compiled-code 依赖必须在 `server.js` 的 global 注入表注册。
- 修改 LLM 核心 64092 时同步六个 definer；本方案应尽量避开这项修改。
- 新 API 路由需要同步三个路由 manifest。
- 不触碰 `.next/node_modules`、OCR 模型或 `deps.zip`；如无法避免，重建 release-runtime-manifest 并更新 `main.js` 中的固定哈希。
- Electron main/preload 变更才需要重打 app.asar 并重写 EXE 完整性；本方案首版不应涉及 Electron 层。

## 9. 范围防漂移

以下变化必须先更新 `WORKSTATE.md` 的“范围变更候选”，说明原因、收益和新增风险，得到用户明确指示后才能执行：

- 扩展固定伙伴槽位；
- 新增外部 RAG、向量数据库或在线嵌入服务；
- 自动联网更新资料；
- 修改认证、账户目录或能力令牌协议；
- 修改 Electron main/preload；
- 添加后台定时世界模拟；
- 大规模前端重构；
- 修改 LLM 64092 核心；
- 将资料档案纳入发布包。

开发模型不得以“顺手优化”为理由扩大范围。

## 10. 停止条件

遇到下列情况停止依赖修改，先记录到 `WORKSTATE.md`：

- 同一个失败根因连续三轮未解决；
- 需要改动未在计划中的认证或 Electron 层；
- 发现数据可能跨账户、跨 world 或跨 companion instance；
- 现有世界文件格式与设计假设不一致；
- 用户最新目标与 WORKSTATE 当前目标冲突；
- 为通过测试需要弱化权限、知识边界或原子性；
- 资料许可或来源无法追溯，且计划要求把正文纳入发布包。

记录事实和证据后再决定是否调整架构，不能通过关闭检查继续推进。
