# 开发模型工作协议

本文件约束所有继续实现共享世界功能的开发模型。唯一持续维护的注意力锚点是同目录的 `WORKSTATE.md`。

## 开发回合开始

按顺序执行：

1. 完整阅读项目根目录 `AGENTS.md`。
2. 完整阅读 `docs/shared-world-continuity/WORKSTATE.md`。
3. 只阅读与 WORKSTATE 当前任务直接相关的本目录方案文件和代码。
4. 用实际工作树、代码和测试结果核对 WORKSTATE，不假设旧记录仍然正确。
5. 在修改代码前更新 WORKSTATE 的“本回合执行契约”。

本回合执行契约必须写明：

- checkpoint ID；
- 本回合唯一目标；
- 明确不做的范围；
- 预计修改的文件；
- 必须保持的三个以内关键不变量；
- 一个最小验证命令；
- 完成判据。

没有这段记录，不开始代码修改。

## 开发过程中的强制重读和写入

以下任一时点出现时，重新读取 WORKSTATE 顶部的“当前目标、关键不变量、下一步”，然后更新对应状态：

- 从资料或设计切换到代码；
- 从一个模块切换到另一个模块；
- 即将修改原计划之外的文件；
- 遇到测试失败、运行时错误或新风险；
- 一次连续工作修改了三个文件；
- 完成一个可独立验证的切片；
- 上下文被压缩、开发模型被更换或会话恢复；
- 准备运行测试；
- 准备声称完成。

“不断读写”不是机械追加流水账。每次更新都要让顶部当前状态保持准确；详细证据追加到日志区。若没有新的事实，不伪造更新。

## 每个切片的循环

```text
读 WORKSTATE
  → 写本切片目标与边界
  → 检查相关代码和现有测试
  → 做最小修改
  → 运行最小验证
  → 把命令、退出码、证据写回 WORKSTATE
  → 重新读取“下一步”再继续
```

不得先做一大批修改，最后一次性回填记录。

## 偏移检测

开发模型准备执行任何动作前，用下面四个问题检查：

1. 这个动作直接推进 WORKSTATE 中的当前目标吗？
2. 这个文件在本回合预计修改清单中吗？
3. 这个动作会破坏任何关键不变量吗？
4. 做完后用哪个已写明的验证命令证明它有效？

任一问题无法回答时，停止修改，在 WORKSTATE 的“偏移／新发现”记录事实。范围变化需要用户明确指示时，不自行推进。

## WORKSTATE 维护规则

- 顶部必须保持简短，开发模型一次读取即可恢复当前任务。
- 使用状态：`[ ]` 未开始、`[~]` 进行中、`[x]` 有证据完成、`[!]` 阻塞或风险。
- “完成”必须附新鲜验证命令和退出码。
- 失败记录不得删除；后续注明根因和处置。
- 设计决策写明“决定、原因、证据、影响”，不要只写结论。
- 修改文件列表只记录本功能触及的文件，不把工作树既有脏文件算作本任务修改。
- 每个 checkpoint 结束时明确写出唯一下一步。
- 文件超过约 400 行时，把已完成的详细日志移到 `history/`，但在 WORKSTATE 保留阶段摘要、关键决定、未决风险和归档链接。
- 不在 WORKSTATE 写 API key、令牌、用户隐私或大段模型输出。

## 与用户沟通

- 进展报告以 WORKSTATE 中已验证事实为依据。
- 用户提供新约束时，先更新当前目标和不变量，再改代码。
- 用户询问状态时，报告完成项、证据、风险和下一步；不要用计划冒充结果。
- 用户要求停止时，先把当前文件状态、未完成验证和安全恢复点写入 WORKSTATE，再停止。

## 禁止行为

- 不跳过 WORKSTATE 直接根据聊天记忆继续开发。
- 不把 WORKSTATE 当成用户授权的替代品。
- 不为了让记录看起来顺利而删除失败或缩小风险描述。
- 不同时推进两个互不依赖的实现目标。
- 不在没有证据时将状态标为 `[x]`。
- 不因剩余上下文较少而扩大批量修改或减少必要验证。
- 不把完整网页、完整测试输出或生成代码粘进 WORKSTATE；记录路径、摘要和命令即可。
