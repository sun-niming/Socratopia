# 架构与实施阶段

## 1. 现状判断

当前运行时已经读取：

- 世界背景 `story.md`；
- 当前角色 `npc_a.md` 至 `npc_d.md`；
- 每个角色对玩家的 `relation_npc_*.md`；
- `pal_moments.md`、`learner_profile.md`；
- 近期群聊 `groupchat/recent.md`；
- 当前教材窗口、进度与课堂摘要。

群聊会同时读取四个伙伴的人设，因此已有多人接话基础。当前连续性提交会写相处片段、角色对玩家的关系、日记、世界学习记录和教材进度。现有不足是：固定四槽、缺少角色之间的动态关系、缺少角色位置和场景状态、共享记忆容量小、世界记录只含简短学习事件，以及世界资料没有独立的本地检索入口。

当前 `local-kb` 适配器只使用调用方已经提供的文本，不搜索整个本地资料库；通用 RAG 适配器需要外部端点。因此“上传世界资料为教材”不能自然覆盖一对一对话与群聊，也会混淆教学依据和世界设定。

## 2. 目标架构

```text
用户输入
  │
  ├─ 账户 / profile / world / companion 身份解析
  │
  ├─ 场景解析：时间、地点、在场者、请求意图
  │
  ├─ 常驻模板：story.md + 当前相关 npc_*.md
  │
  ├─ 动态快照：world state + character state + relationships
  │
  ├─ 权限过滤：剧情截止点 + 角色知识范围 + 见证范围
  │
  ├─ 世界知识检索：最多若干条相关、可追溯的 lore cards
  │
  ├─ 提示上下文编译：固定预算、数据边界、来源标识
  │
  ├─ 一对一回复或多人场景生成
  │
  └─ 成功后提交：事件日志 + 状态变化 + 关系变化 + 记忆传播
```

所有读取与写入都必须绑定经过服务端验证的账户、档案和世界。客户端只能表达意图，不能通过路径、角色名或任意 worldId 绕过服务端解析。

## 3. 模块边界

建议在 `resources/server/lib/` 下新增手写模块，避免把核心逻辑直接写进编译 bundle：

| 模块 | 单一职责 |
|---|---|
| `world-lore/card-schema.js` | 校验与规范化知识卡，不负责检索 |
| `world-lore/index-store.js` | 读取本地索引，管理缓存与版本，不生成内容 |
| `world-lore/retriever.js` | 根据场景和角色权限返回少量证据卡 |
| `world-state/store.js` | 读取世界、角色和关系快照 |
| `world-state/event-commit.js` | 通过现有事务层原子提交事件及派生状态 |
| `world-context/compiler.js` | 把模板、状态、记忆和知识证据编译成受限上下文 |
| `world-context/scene-selector.js` | 从固定伙伴中选择在场者和发言候选，不生成最终台词 |

编译路由只通过 `server.js` 安装的 `global.*` 句柄访问这些模块。不得在 `.next/server/chunks/*.js` 新增 `require("fs")`。若没有必要修改 LLM 核心模块 64092，就不触碰它；如确实触碰，必须同步六个 definer。

## 4. 数据源与运行时分离

项目根目录 `资料/` 是不可变证据档案。运行时不直接读取网页 HTML，也不把整个资料目录复制到每个用户世界。

派生流程：

```text
资料/来源原文 + 资料/可用文本
       ↓ 人工或受控脚本提炼
资料/知识卡草稿
       ↓ schema 校验 + 来源核对
发布包中的基础 lore cards
       ↓ 创建世界时复制/引用
账户隔离的 world lore index
```

原始来源、派生卡和玩家世界新增事实分开保存：

- `source_canon`：来自可追溯原著资料，不可被运行时覆盖；
- `derived_summary`：从原著资料概括，必须保留来源；
- `local_canon`：玩家与角色在该存档中实际创造的事件；
- `hypothesis`：尚未确认的推断，不可写成事实。

## 5. 实施阶段

### 阶段 A：内容契约与最小样本

目标：不改聊天路由，先证明资料可以被可靠提炼。

- 为翁法罗斯和提瓦特各选择一个明确剧情截止点。
- 每个世界只制作一份世界核心、四份角色模板和 30 至 50 张知识卡。
- 知识卡覆盖：公共常识、地点、两段历史、四人关系、至少两项秘密。
- 校验来源、时间、知识范围和冲突字段。

完成定义：任何知识卡都能追溯到 `资料/` 中的来源 ID 和 URL；同一秘密不会被无权限角色检索到。

### 阶段 B：本地世界知识检索

目标：不引入外部服务，完成确定性的本地检索。

- 首版使用标签、别名、人物、地点和关键词评分；中文关键词通过显式别名表补足。
- 只有检索质量确实不足时，才提出嵌入模型或向量库方案。
- 检索输入包含 world、canon cutoff、speaker、participants、location 和 query。
- 返回有限条目、总字符上限和完整来源元数据。

完成定义：角色能检索到相关公开知识，不能检索未来剧情、他人私密经历或另一个世界的资料。

### 阶段 C：动态世界状态与事件提交

目标：同一事件能够产生有限、可解释、可回滚的状态变化。

- 保存世界状态、角色状态、角色间有向关系和事件日志。
- 只有已经输出给用户或明确发生的事件才能提交。
- 用事件 idempotency key 防止重试重复写入。
- 使用现有 companion-continuity 事务层统一提交相关文件。
- 记忆只传播给参与者、见证者或明确听闻者。

完成定义：三名角色亲历同一事件，第四名不在场；重启后前三名可正确提起，第四名保持未知。

### 阶段 D：一对一与群聊统一上下文

目标：两条入口读取相同的世界事实和动态状态。

- 在 chat 与 groupchat 生成前调用同一 `world-context/compiler`。
- 不复制两套检索、权限和预算逻辑。
- 群聊场景从在场者中选择 1 至 3 名发言者，不强迫所有角色轮流发言。
- 一对一角色可以引用合理可知的群聊和共享事件。

完成定义：相同场景在一对一和群聊中不出现时间、地点、关系或知识冲突。

### 阶段 E：场景 NPC 与生活演化

该阶段在 A 至 D 验收后再做。

- 固定四槽继续代表长期伙伴。
- 其他原著角色作为按场景加载的临时 NPC，不立即扩展固定槽位。
- 玩家重新进入世界时，可根据经过的时间生成“候选变化”，必须在第一次相关互动中确认后才能成为永久事实。
- 不运行无限后台模拟，不在玩家不知情时持续消耗模型调用。

完成定义：背景角色可以自然出现并影响场景，同时不获得固定伙伴的私人关系和记忆权限。

## 6. 明确延后事项

- 扩展到几十个常驻独立角色；
- 实时自治代理和常驻后台世界；
- 向量数据库与在线嵌入服务；
- 自动抓取或自动更新外部 Wiki；
- 复杂经济、战斗或地理模拟；
- UI 世界编辑器大改；
- 将原著全文放入每轮提示。

这些能力只有在最小四人世界通过长期连续性验收后才进入决策。
