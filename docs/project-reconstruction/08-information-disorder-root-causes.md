# 信息为什么会乱：根因分析

> 批次 B-4（2026-09-14）。回答"这个项目怎么会变成现在这样"。
> 证据 E-150 ~ E-165。本文件是**成因分析**，不是历史叙述；历史见 `03-timeline.md`。
> 与 `DECISIONS.md` D-010（无源码）配套阅读。

---

## 0. 一句话

混乱不是"有人乱建文件"造成的，而是**三条结构性约束叠加**的必然产物：
**无源码（只能改编译产物）** × **无构建回归（只能靠手工 smoke 保底）** × **无版本保护纪律（大量关键文件不进 git）**。

在这个环境里，唯一可行的做事方式就是"就地小步补丁"，而**就地小步补丁必然产生副本、覆盖层和口头约定**。副本、覆盖层和口头约定积累半年，就是现在看到的样子。

---

## 1. 六个具体机制（每个都有实证）

### M1 没有真源，所以真源是"当前盘上文件"

- **已证实**：无源码仓库（E-130）。产物的唯一权威副本就是工作区本身。
- **后果**：任何"版本"概念都退化为"这个文件现在的样子"。没有 diff，没有 tag，没有发布号（E-001：无 tag、无 release notes）。
- **可观察症状**：`AGENTS.md` 说的数字（28 routes / 20+ smoke）与实测（34 / 146，E-045/E-060）脱节，且**没人会察觉**——因为没有一个"应该是什么"的基准。

### M2 就地补丁需要"保底副本"，于是产生文件级克隆

- **已证实**：`resources/` 下同时存在 `settings.json`、`settings - 副本.json`、`settings - 副本 (2).json`、`settings__.json`——**一份配置四个文件**，靠文件名区分，git 又不跟踪它们（E-150）。
- **已证实**：`outputs/` 里同一份 OCR 方案有 **9 个版本**：`OCR_TRANSCRIPTION_PLAN.md` → `_REVIEWED` → `_APPROVED` → `_APPROVED_V2` … `_APPROVED_V6` → `_FINAL`（E-151）。
- **机制**：改之前先复制一份，改完不清理。V2…V6 说明连"复制"都没能解决问题，只是在文件名上叠代。
- **后果**：读文档的人**无法判断哪个是当前有效的**——`_FINAL` 未必是最后修改的，`_APPROVED_V6` 也未必比 `_FINAL` 旧。

### M3 前端产物靠"人工命名覆盖层"打补丁

- **已证实**：`.next/static/chunks/app/` 里除 webpack 哈希名（`page-3a1fef7566e26c43.js`）外，还有**带日期和人名的**：`page-practice-ui-20260622.js`、`page-practice-ui-20260625-jyfix.js`、`page-practice-ui-20260626-postclass-notes.js`（E-152）。
- **机制**：webpack 产物的真名是内容哈希，人工改完没法回写哈希，只能另存一个可读名的文件当覆盖层。
- **后果**：一个页面由**多个 chunk 叠加**构成，加载顺序决定谁盖谁。要搞清"练习 UI 现在到底长什么样"，必须同时读三个补丁层——且要先确认它们的加载顺序（→ Q-011 仍未解答）。

### M4 主动删过历史文档，而且删在"无替代"的时候

- **已证实**：两次删除事件。
  - `ca07d17`（2026-08-14）删 `CLAUDE.md`(400 行) 与 `docs/knowledge-source-provider/*`(3 文件)
  - `06c0256`（2026-08-26）删 `RENAME.md`(201 行，项目自述史) 与 `改动日志.md`(193 行)
  （E-080/E-081/E-082、Q-008）
- **机制**：判断为"过时"就删。但因为没有替代文档，删完信息就**只剩在 git 深处**，而 `RENAME.md` 恰是唯一一份完整项目史。
- **后果**：现在要重建历史，第一步是"从 git 捞尸体"（本工作的批次 B-1）。`RENAME.md` 的作者自己在文末写"如何阅读这段历史"——说明写得很好，只是被删了。
- **讽刺点**：删除者删的是**唯一的历史记录**，理由是"outdated"。而真正过时的是 `AGENTS.md`（数字全错），它却被保留。

### M5 工具被删，但引用没改

- **已证实**：`fix-asar-integrity.js` 被 `4f1f907`（2026-08-30）删除（E-092），且工作区至今仍是"未提交的删除"状态（E-004）。
- **已证实**：`AGENTS.md` 与 `CLAUDE.md` **都还在教** `node fix-asar-integrity.js`。
- **后果**：按文档重打包 ASAR，最后一步会失败，且失败原因看起来像环境问题。工作区半提交状态本身也说明"改到一半停了"。

### M6 指令文件互相打架，且都说自己是对的

- **已证实**：
  - `AGENTS.md`（08-31）开篇声称"之前的 `CLAUDE.md` **在本仓库缺失**"，"本文件是唯一指令文件"——实际 `CLAUDE.md` 存在（E-011、Q-009）。
  - 两者对 server 是否复制到用户目录**直接矛盾**——`AGENTS.md` 错（Q-004，E-100）。
  - 两者都引用**不存在的兄弟副本** `Socratopia_2.0`（E-070、Q-001）。用户已更新 `CLAUDE.md` 修正了别的问题，但**第 12 行这条仍在**。
- **后果**：新人和新会话第一天就会拿到错误的世界观；且因为两个文件都"看起来权威"，会来回摇摆。

## 2. 三个放大器（让上面的问题持续恶化）

### A1 分支与游离提交从不合并

- **已证实**：`master` 上有一条从未合入 `codex/push` 的提交 `cb74cdd Scope practice data and tutoring sessions by account`（E-090）。
- **已证实**：另有 **4 个游离提交** `d986417`/`8bfa3af`/`5a0c495`/`feb5ca9`（均 2026-08-12 "Codex worktree snapshot: archive-cleanup"），**不在任何分支 tip 上**（E-091）。其中 `feb5ca9` 正是删掉 400 行 `CLAUDE.md` 的那次。
- **后果**：同一个人（或同一批 agent）在不同分支上做了互相冲突的整理，**谁都没合回来**。今天盘上的 `CLAUDE.md` 是"被删后又重新落盘"的无跟踪文件——它的祖先是删除它的那次提交（E-093）。

### A2 几乎不跟踪文件

- **已证实**（E-093）：仓库根只有 16 个文件被 git 跟踪。以下**全部未跟踪**：
  `CLAUDE.md`、`AUTO_ADVANCE_WINDOW_REPAIR_CHANGELOG.md`、`LLM_THINKING_FIX_CHANGELOG.md`、`MATH_SPEECH_CORE_*.md`(3)、`POST_CLASS_SAVE_FIX_2026-09-13.md`、`DEEPSEEK_V4_FLASH_CLASSROOM_*`(3)、`PROJECT_MATH_SPEECH_DOSSIER/`、`角色/`、`tools/`、`outputs/`、`tmp/`。
- **后果**：**2026-08-31 之后的全部工作（近半个月、也是量最大的阶段）没有版本历史**。一次误删、一次磁盘故障，即永久丢失。`tmp/` 名叫临时，实际装着 `import-character-library.py`、`optimize-character-templates.py` 等**唯一一份**脚本（E-153）。

### A3 多份打包产物并存，无权威标记

- **已证实**：`resources/`（当前）、`win-unpacked/`（08-26）、`release/win-unpacked/`（08-29）、仓库外 `/e/huanjing/AAA/`（07-23，E-071）。`resources/app.asar` 有 4 个不同版本（E-058、Q-006）。
- **后果**：改 Electron 层时**很容易改错文件、或改对了但被旧 asar 覆盖**。用户已更新 `CLAUDE.md` 新增"Two copies of the runtime"一节说明 `win-unpacked/` 是提交快照——这本身就是"乱"催生的补丁式文档。

## 3. 哪些是"结构性必然"，哪些是"本可避免"

| 类别 | 项目 | 判断 |
|---|---|---|
| **结构性必然**（无源码的直接后果） | M1 无真源、M3 前端覆盖层、A3 多产物并存 | 在"只能改编译产物"前提下，**基本无法避免** |
| **本可避免**（纪律问题） | M2 副本堆叠、M4 删历史、M5 删工具不改引用、M6 文档打架、A1 不合分支、A2 不跟踪文件 | 全都**不需要任何技术前提**就能做对 |
| **放大器** | A1/A2/A3 | 二者叠加才让"可避免的"变成"已发生的" |

**关键结论**：**混乱的主要成因不是"没有源码"，而是"在没有源码的情况下没有建立最低限度的记录纪律"。** 理由：无源码意味着每次改动都不可逆、不可重建，因此**本应比有源码的项目更需要**文档与版本保护——实际却相反，关键文档反而被删、被排除在版本控制外。

## 4. 混乱的具体代价（可验证）

1. 一次"改 LLM 行为"要同时改 **8 处**模块 64092 副本（CLAUDE.md/AGENTS.md 有记）。
2. 一次"改鉴权语义"要同时改 **5 份**内联 account-helper 副本——**两份指令文件都没记**（E-141，本工作批次 C-2 才发现）。
3. 一次"改群聊语音"要同时改前端 `4137` chunk 与服务端 `3461` chunk 的重复语音库（E-017 记载二者"内容基本重复"）。
4. 想知道"练习 UI 现在什么样"，要读 3 个补丁层并先确认加载顺序（M3，Q-011 未解）。
5. 想确认"当前有几个路由"，文档说 28、实测 34（M1/E-045）。
6. 想重建历史，第一步是从 git 捞被删文件，而**半数史料根本不在 git 里**（A2）。

## 5. 对重构路线的直接含义（重构建议，非事实）

1. **先做"权威标记"，再谈重构**：明确哪份产物/哪份文档是当前有效，其余标注归档。成本低、收益立竿见影。
2. **把未跟踪的东西纳入版本控制**，优先级高于任何代码重构——否则重构本身也不会有历史。
3. **给"必须同步改的多处"建一张清单**（64092 的 8 处、account-helper 的 5 处、语音库的 2 处、3 个 manifest），并尽量用脚本校验一致性。
4. **消灭文件级克隆**：配置副本合并为一份 + 明确回滚手段；文档多版本改为"一份 + 文内变更记录"。
5. **两个指令文件合一**或明确主从关系，并建立"文档里的数字会被实测校验"的机制（哪怕只是一个 `tools/verify-docs.js`）。
6. `tmp/` 里那些**唯一副本脚本**要提升为正式工具（`tools/`）并跟踪。

> 各条的具体验收条件、回滚办法、优先级排序，留到阶段 E 的 `06-refactor-roadmap.md` 展开。本文件只负责**把成因和代价钉死**，供路线引用。
