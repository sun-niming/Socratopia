# Socratopia 魔改历程

> 这是一份针对 **Socratopia Windows 打包版** 的补丁史。
>
> 当前仓库没有可用于重新生成产物的完整构建流水线。历次改造主要直接发生在 Electron、Next.js 服务端和 React 的编译后 bundle 上。因此，这里的“魔改”既包括功能扩展，也包括对打包产物的逆向定位、补丁注入、运行时挂载和回归保护。

## 一句话概括

Socratopia 最初只是一个可运行的苏格拉底式 AI 教学桌面应用；这条分支逐步把它扩展成了一个带有 **自适应教学、教材知识图谱、出题练习、教学进度锚定、PDF 精读、多知识源检索、长推理检查、课后记忆和本地语音优化** 的实验性学习系统。

## 项目是怎么被“魔改”的

运行时仍然保留原应用的三层结构：

1. Electron 主进程负责启动应用、暴露本地能力和管理 Next.js 子进程。
2. Next.js 服务端提供聊天、教材、练习、知识源、精读等 API。
3. React 前端负责课堂、伙伴、教材和练习界面，通过 preload 与 Electron 通信。

真正特殊的地方在于：仓库保存的是 Windows 成品包及其解包后的编译结果，而不是完整源工程。于是改造形成了一套自己的生存方式：

- 直接修改 `.next/server/app/api/*/route.js` 和共享服务模块；
- 在压缩后的 React chunk 中补 UI 和交互；
- 通过 `server.js` 把新增模块挂到 `global`，供 webpack bundle 调用；
- Electron 改动同时维护根目录副本和 ASAR 解包副本；
- 用大量自包含 smoke test 弥补没有原始测试与构建流水线的问题；
- 用 API manifest 补丁、ASAR 完整性修复和语法检查保证成品仍能启动。

## 时间线

### 2026-06-17：建立轻量补丁仓库

提交 `b7ad6eb` 将 Windows 打包产物纳入版本管理，确立了“以成品为基线、对编译结果做小步补丁”的维护方式。

这一阶段也留下了最早的一批语音侧改造：

- 梳理课堂与群聊的伙伴语音模型映射；
- 为 GPT-SoVITS 增加预热、推理参数调整和缓存方案；
- 将群聊语音改为按发言人排序派发，并降低并发以避免乱序；
- 尝试课堂流式播放和逐句返回，减少长回复的首句等待时间。

同时加入 `fix-asar-integrity.js`，解决 Electron ASAR 重打包后完整性校验失效的问题。这一步为后续修改 Electron 主进程和 preload 奠定了基础。

### 2026-06-18：从“聊天应用”迈向自适应教学

连续四次提交完成了第一轮能力铺设：

- `6a3db1e`：验证在打包后的 Next.js 中注册新 API 路由；
- `9f72251`：增加路由脚手架，自动处理 route 与 manifest；
- `c926129`：加入自适应教学数据层和首批 smoke test；
- `e53d153`：一次性落地自适应教学、练习系统和长推理实验的主体。

这一轮是项目第一次大规模扩展，主要包括：

- 课程、学生、会话和掌握度数据模型；
- 教材概念图谱抽取与诊断代理；
- 模型路由与高阶模型配置；
- `/api/adaptive-teaching`、概念图谱、诊断和长推理实验路由；
- `/api/practice` 的出题、判题、提示、讲解和变式题能力；
- 练习工作台前端；
- 练习记录、错题和教学会话持久化；
- 长上下文、长边连接、边审计、批量检查与构建前检查；
- 教学结束后的进度恢复基础设施；
- 面向打包产物的补丁脚本和成套 smoke test。

从这一阶段开始，项目不再只依赖一个巨型聊天 Prompt，而是尝试将“诊断—规划—教学—评价”拆成可观察、可测试的服务能力。

### 2026-06-25 至 2026-06-27：把教学进度钉在教材上

早期功能虽然丰富，但课堂推进容易被模型自由发挥带偏。随后几次提交集中处理“讲到哪一页、什么时候能翻页、下课后从哪里继续”的确定性问题。

- `42ce3de` 恢复 Markdown 原始窗口教学路径，引入进度游标；
- `732fac0` 将打包版课堂进度锚定到教材内容；
- `1d25b3b` 增加 progress guard，并统一下课时的进度锚点；
- `adc66db` 修正 Markdown 进度下的自动推进；
- `f253e3a` 收紧课堂规则，减少聊天逻辑绕过教学约束的机会。

这轮改造形成了几条关键原则：

- 模型可以组织讲法，但不能随意宣布已经讲完未覆盖的内容；
- 当前页、已读范围和阶段切换由服务端守卫约束；
- “下课并保存”必须先完成状态绑定和进度归一化；
- 恢复课堂时优先读取持久化锚点，而不是猜测上下文；
- Markdown 教材窗口与知识库抽取路径要保持一致。

### 2026-06-29：补齐多知识源路由的工程能力

知识源模块开始从单一本地知识库扩展为 provider 架构，支持本地 KB、RAG、搜索、数据库、Kimi 客户端和桌面桥接等候选来源。

围绕 Phase 1 验收，补上了几个容易在真实运行中出问题的环节：

- provider 级超时和结构化延迟日志；
- 指数退避重试；
- 可禁用缓存和可禁用 provider；
- 外部 `configure()` 配置入口；
- 证据标准化、缓存、可信度策略和来源路由；
- 对 Kimi Desktop 本地结构及 Daimon Control WebSocket 的只读兼容性调查。

这部分工作的核心不是“搜得更多”，而是让外部证据具有来源、状态、延迟、可信度和失败降级，不让某个 provider 卡死课堂主流程。

### 2026-07-21：修复教材抽取与课堂续接

提交 `ef5e1dc` 是一次偏稳定性的集中修复，解决 PDF 教材和教学进度在真实资料上的问题：

- 强化 PDF 文字层、CMap 和页面提取；
- 在 Windows 上增加 OCR 降级路径；
- 增加知识库发布器和质量门禁；
- 增加知识库构建进度与 SSE 通知；
- 修复课堂结束、练习路由和阅读范围的集成问题；
- 增加教材修复工具；
- 为真实 PDF、知识库构建、下课保存和恢复流程增加集成测试。

这一阶段的改造目标很朴素：教材必须真的能读出来，进度必须真的能保存下来，失败时不能悄悄产出一份看似成功的空知识库。

### 2026-08-06 至 2026-08-14：加入独立 PDF 精读与知识连接层

8 月的重点是 `/Close_Reading` 独立精读链路。它支持指定 PDF 页码或范围进行解释、翻译、逐行分析、摘录和对照，并在文字层不可用时按需渲染页面、调用视觉模型转录。

精读功能刻意与普通课堂隔离：

- 不自动推进教材页码；
- 不污染常驻课堂 Prompt；
- 不把原始页级证据写入知识库；
- 只有用户明确要求记忆时才生成课后候选；
- 缺页、越界、视觉未配置或模型失败时有界降级，不猜写教材内容。

提交 `ca07d17` 还把知识 provider、Daimon bridge、证据缓存、信任策略和精读菜单一起纳入成品包，使“课堂内部知识”与“外部检索证据”之间有了正式连接层。

### 2026-08-19：适配 Responses API，并延长概念图谱缓存

提交 `7b5f473` 继续清理模型接口兼容问题：

- 增加 Responses API 兼容层与专门回归测试；
- 完善精读视觉转录与原生 Responses fallback；
- 改进精读的最近记忆上下文；

由于 LLM 核心模块在多个编译文件中重复内联，这类改动也推动仓库形成了“所有定义副本必须同步修改”的硬约束。

### 2026-08-21：第二代自适应教学闭环正在成形

当前工作区还有一批尚未提交的改造，应视为 **进行中状态**，而不是已发布能力。它们试图把第一代自适应教学从“若干代理和数据文件”升级为有明确事务边界的闭环系统。

目前可以看到的方向包括：

- `assessment-engine`：统一评估入口；
- `evidence-ledger`：记录可追溯的学习证据；
- `mastery-engine`：根据受信证据更新概念掌握度；
- `policy-engine`：根据状态选择下一步教学动作；
- `orchestrator`：协调一轮教学的准备、执行与提交；
- `storage-v2`：新版持久化结构；
- `transaction-journal`：为跨文件写入提供事务日志和恢复能力；
- `chat-service`：将自适应决策接入聊天链路；
- `external-evidence-service`：约束练习、卡片等外部证据如何进入掌握度模型；
- `llm-gateway`：收拢模型调用入口；
- 本地请求认证、账户上下文、Electron 能力声明和前端适配。

设计上最重要的变化是：不是所有用户行为都能证明“学会了”。系统开始区分已验证作答、提示后作答、普通聊天、阅读和模型推断等不同等级的证据，并尝试通过事务提交保证“回复已经输出”和“状态已经落盘”不会互相打架。

## 这条分支最终改变了什么

| 维度 | 原始形态 | 魔改后的方向 |
|---|---|---|
| 教学 | 以聊天 Prompt 驱动 | 诊断、策略、教学、评价组成闭环 |
| 教材 | 阅读与聊天上下文 | PDF 抽取、OCR、知识图谱、进度锚定 |
| 练习 | 零散卡片能力 | 出题、判题、提示、讲解、变式和错题记录 |
| 进度 | 容易随对话漂移 | 游标、守卫、下课归一化与恢复 |
| 知识 | 主要依赖本地上下文 | 多 provider、证据标准化、可信度与缓存 |
| 精读 | 普通课堂里临时询问 | 隔离的页级 PDF 证据工作流 |
| 推理 | 单轮模型调用 | 长上下文和知识图边的批量审计工具 |
| 记忆 | 会话级记录 | 明确候选、课后写入和副作用边界 |
| 语音 | 基础 TTS | 预热、缓存、顺序派发与流式播放实验 |
| 工程 | 常规源码构建 | 对编译产物打补丁，以 smoke test 保底 |

## 魔改过程中形成的工程规矩

这条分支最有价值的产物之一，是一套对“无源码成品包”仍可持续维护的规则：

1. `resources/server/.next/server/chunks/*.js` 不能直接 `require("fs")`，必须使用预先注入的 `global.__FS__`。
2. LLM 核心模块 64092 存在多个定义副本，修改模型逻辑时必须同步全部副本。
3. API 路由不仅要改 `route.js`，还要保持 Next.js manifest 注册一致。
4. Electron 主进程与 preload 必须同时修改根目录和 ASAR 解包目录，随后重打包并修复完整性。
5. 压缩 bundle 中的字符串必须谨慎转义，并用语法解析器定位错误。
6. 每个新增服务模块尽量配套独立 smoke test；涉及课堂主链时再补端到端测试。
7. 教材进度、知识库、精读证据和自适应掌握度之间必须有明确副作用边界。
8. API 密钥、用户数据、`settings.json`、`set.json` 和重打包的 `app.asar` 不进入提交。

## 尾声

这条分支的演进路线并不是“推倒重写”，而是在一个已经封装好的桌面应用上不断寻找稳定接缝：先让新路由能注册，再让数据能落盘；先让教材能被可靠读取，再约束课堂进度；先接入更多知识，再为证据建立可信边界；最后才尝试把教学决策做成可恢复、可审计的事务闭环。

它因此更像一座持续加固的实验场：外表还是 Socratopia，内部已经逐渐长出一套面向真实教材、真实课堂和真实失败场景的 AI 教学基础设施。
