## 2. 根因（Q-051 已解答）

### 2.1 谁在竞争
`chat/route.js:917`：
```js
_advanceComplete = await global.__AUTO_ADVANCE__.completeTurn({...});
_advanceComplete.shouldPrefetch && global.__AUTO_ADVANCE__.prefetchCandidate({...})
  .catch(...)                       // ← 注意：没有 await
```
**后台预取是"发射后不管"**，与同一轮的**前台收尾保存**并发。

而两者都会写 `textbook_index.json`：
| 写入者 | 位置 | 触发 |
|---|---|---|
| `auto-advance.updateIndexCurrentPage()` | `auto-advance.js:519-532`（由 `projectConversation` 调用） | 后台 `prefetchCandidate` |
| `kb-progress.syncTextbookCurrentPage()` | `kb-progress.js:1126-1141` | 前台收尾 |

### 2.2 为什么防护失效
- auto-advance 内部**有 `withLock(scope)`**，但它只序列化 **auto-advance 自己**的入口（`bootstrap`/`readSnapshot`/`beginTurn`/`completeTurn`/`commitTeachingProgress`/`commitRange`/`prefetchCandidate` …，共 11 处）。
- **`kb-progress` 不是该把锁的参与者**——它靠自己的 `atomicWrite` 重试来防。
- 于是两侧各用**重试**对抗，且预算不一致：

| 写入者 | 重试次数 | 退避 | 总窗口 |
|---|---|---|---|
| `auto-advance.js:140` | **5**（`attempt >= 4`） | 25ms×(n+1) | **≈375ms** |
| `kb-progress.js:1105` | 10（`attempt >= 9`） | 20ms×(n+1) | ≈1.1s |

**窗口短的那一方先放弃** → 异常从 auto-advance 的 `atomicWrite` 抛出（后缀为数字，正是 `write-file-atomic` 的 `getTmpname()` 特征，而全仓库只有 auto-advance 用该库），冒泡到 `kb-progress.js:1404` 的外层 catch，整轮保存作废。

### 2.3 时间关联
09-11 之前日志无 EPERM，09-11 起出现 → 与当日 auto-advance v2 重写吻合（新引入或新暴露）。
另外 `kb-progress.js:1320` 的 `authoritativeProgress` 仅在 `advanceProtocolVersion === 2` 时为真；为假时走 `syncTextbookCurrentPage`（**无锁**）而非 `commitTeachingProgress`，这条路径天然更易与后台预取相撞。

## 3. 修复（最小、对齐仓库既有做法）

`resources/server/lib/reading/auto-advance.js:140-158`：
```diff
-      if (process.platform !== "win32" || attempt >= 4 || !error || error.syscall !== "rename" ||
+      if (process.platform !== "win32" || attempt >= 9 || !error || error.syscall !== "rename" ||
           ["EPERM", "EACCES", "EBUSY"].indexOf(error.code) < 0) throw error;
```
即把重试预算由 5 次/≈375ms 提到 **10 次 ≈1.4s**（与 `kb-progress.js` 同级，略宽）。
并加注释写明 BUG-0012 的来由与"预算不得再调窄"的约束。

**为什么选这个而不是加锁**：仓库里已经有"用重试对抗 Windows 竞争"的成熟先例（`kb-progress.js`、`auto-advance.js` 自身），对齐预算是 1 行改动、语义一致、回滚容易；引入跨模块锁是更大的重构（已记入 C3/C5 候选）。

## 10. 决定性证据：失败时延精确等于"整条新预算"

对每次失败，量取"距上一条带时间戳的日志行"的毫秒数：

| 时点 | 时延 |
|---|---|
| 生效前 18 次 | 328、333、334、335、340、390、423、427、428、432、432、435、439、455、457、499、610 … |
| 生效后 6 次 | **1265、1253、1255、1257、1270、1250** |

推导：旧预算 = 退避 25+50+75+100 = **250ms**；新预算 = 25+…+225 = **1125ms**。
实测均值 430ms → 1255ms，**差值 ≈825ms ≈ 新增的 875ms 退避**。

**关键在于离散度**：生效后 6 次的极差只有 **20ms**（1250~1270）。说明每次都是**把整条预算烧光才抛**，而不是"撞上随机的外部瞬时占用"——后者会给出散布很宽的时延，且常常在预算内自愈。

→ **加宽预算在结构上不可能有效**：不是窗口不够长，是**窗口里阻塞者根本不会松手**。

## 11. 新根因（对 §2 的修正）：同步重试把唯一的解锁者饿死

### 11.1 先排除原假设
§2.1 称"后台预取与前台收尾并发写同一文件"。但实测两侧写入器**都是完全同步的**：

- `auto-advance.js:140` `atomicWrite()` → `writeFileAtomic.sync()`（`Atomics.wait` 退避）
- `kb-progress.js:1105` `atomicWrite()` → `fs.writeFileSync` + `fs.renameSync`（`Atomics.wait` 退避）

Node 是单线程：**两个纯同步写在同一进程里不可能真正交叠**。所以 EPERM 的持有一方不是"另一个同步写"，而是**一个跨越 `await` 的打开句柄**。

### 11.2 实测两条事实（`outputs/bug0012-livelock/repro.js`，本机复现通过）

- **事实 A**：只要**任何**进程对目标文件持有打开的句柄，`fs.renameSync(tmp, target)` 就一直 `EPERM`。Node 不以 `FILE_SHARE_DELETE` 打开，普通只读句柄即可阻塞。
- **事实 B（自锁）**：`Atomics.wait` **阻塞事件循环**。若持句柄的是**同进程的异步 fs 任务**，它的 fd 由 JS 续体 `close()` 关闭——而续体在阻塞期间**永远跑不到**。于是：

```
同步重试开始 → 事件循环停 → 异步持有者的 close() 无法执行 → 句柄一直开着
             → rename 一直 EPERM → 烧光预算 → 抛出 → 事件循环恢复 → 持有者这才 close
```

**复现输出**：
```
A. rename with NO holder (control)
  [control] rename OK on attempt 1 (1ms)
  => PASS: no contention means first attempt succeeds

B. rename while a same-process ASYNC holder has the file open
  [livelock] exhausted 40 attempts (2496ms)
  holderOpened=true holderClosed=false
  => PASS: budget fully burned while the holder stayed open (livelock reproduced)
```

这条机制**同时解释了全部三个观测**：①每次必然烧光整条预算（离散度 20ms）；②~10% 的偶发命中（只有当异步读者恰好在飞）；③**预算从 375ms 加宽到 1.4s 完全没用**。

### 11.3 持有者候选（未逐一定案，Q-054）
`resources/server/.next/server/chunks/2751.js` 的 `async function y()`：
```js
async function y(a,b){ let c=x(a,b); ... JSON.parse(await (0,d.readFile)(c,"utf-8")) }
```
`x()` 拼的就是 `textbook_index.json`。该 chunk 被 `chat/route.js`、`reading-context/route.js`、`textbook/route.js`、`jump-page/route.js`、`groupchat/route.js` **五条路由共用**，而路由层普遍 import `fs/promises`。同进程并发请求（前端轮询 reading-context 等）在该文件上留下短暂只读句柄，与前台收尾保存相撞即可触发自锁。

**合理推断，未定案**：本轮只证明了机制与候选位置，没有在运行时抓到"谁正开着句柄"。

## 12. 修复方向（尚未实施，需授权）

按性价比排序。**都是"消除竞争/消除阻塞"，不是"再加长预算"**：

1. **让失败者主动让出事件循环**（对症）：`atomicWrite` 增加 async 版本，用 `await sleep()` 代替 `Atomics.wait`。但调用方多为同步上下文，改动面较大。
2. **让读者不留句柄**（最小、最对症）：把 `textbook_index.json` 的 `await fsp.readFile(...)` 读者改成 `readFileSync`。同步读**不跨 `await`**，句柄在同一个 tick 内开闭，自锁窗口归零。候选点少（chunk 2751 的 `y()` 及其调用方）。
3. **消灭"两个模块各写同一文件"**（根治，即 §7.3 的 C3/C5）：共享写入器 + 跨模块统一锁。
4. ~~继续加宽预算~~ —— 已由本轮证明单独无效。

**验收条件（与上轮不同）**：不能只看失败率下降，必须看**时延特征改变**——若修复正确，成功路径应在**远小于 1125ms** 处返回；失败时延不再集中于 1255ms。
