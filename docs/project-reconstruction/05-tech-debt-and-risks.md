## 1. 结构性（无法靠纪律解决的）

### R-01 无源码 + 无构建链路
- **影响**：每次改动都不可重建、不可 diff 到源码层；重构无法"回退到源码"。
- **现状**：编译产物即真源（D-010）。`lib/` 里 238 个文件虽是手写、可当普通源码处理，但 **22 个被改写的本体路由 + 全部前端 + Electron 层**都在产物里。
- **关键未知**：重建是否可行（Q-021）。**无 sourcemap**（E-123），但依赖版本完全已知（E-120~E-122）。

### R-02 近半月工作无版本保护
- **影响**：2026-08-31 之后全部文档、`tools/`、`outputs/`、`角色/` 未进 git。一次误操作即永久丢失。
- **已发生的同类事故**：`06c0256` 删掉两份唯一历史文档后，只能靠 git 对象捞回（E-080/E-081）。

## 2. 同步型（同一次改动的多处副本）

### R-03 前端 5 包同步 —— **本仓库最昂贵的一处债**
- **事实**：5 个约 760 KB bundle，浏览器只加载 1 个；其余 4 个靠 `tools/*.js` 硬编码数组 + 字符串断言 smoke 保持同步（E-240/E-241/E-242）。
- **影响**：改前端任一逻辑 = 改 5 × 760 KB；漏一个则"某天真加载了别的 bundle 时"行为不一致。
- **量化**：约 3 MB 死重；`replaceOne` 的"恰好命中一次"校验意味着 5 份内部结构必须长期一致。

### R-09 / R-10 模块 64092（×8）与内联 account-helper（×5）
- **事实**：LLM 核心 64092 有 8 处定义；鉴权 helper 有 5 份内联副本（E-141，**两份指令文件均未记载**）。
- **已发生的后果**：BUG-0002（thinking 开关）与 BUG-0003（截断检测）都要求在 64092 的**全部副本**同步改（E-281/E-282 均明写"六处定义同步"）。
- **风险**：漏改任一副本 → **按路由行为分叉**，且只在特定路由暴露。

### R-04 Electron 双副本 —— 已经漂移
- **事实（实证）**：根 `main.js` 与 ASAR 副本差 45 B、内容不同（E-303/E-305）。
- **影响**：ASAR 是运行时真源 → 根副本的新代码可能**根本没生效**。
- **附带**：`fix-asar-integrity.js` 已被删除（E-092），但两份指令文件仍教它。
  → 已查明**替代工具存在且更好**：`tmp/patch-asar-integrity.js`（幂等、正确哈希算法、E-398/Q-049）——**但它躺在 gitignore 的 `tmp/` 里**，于是又成了一条 R-02 的注脚。

---

### R-21 两套原子写重试预算不一致（BUG-0012）—— **真实使用中每天 3~5 次**
- **事实（实证）**：`auto-advance.js` 的 `atomicWrite` 重试 **5 次 ≈375ms**，`kb-progress.js` 同类函数 **10 次 ≈1.1s**（E-412）；`write-file-atomic` v7 自身不做 rename 重试（E-411）。
- **后果**：`textbook_index.json` 的 rename 反复 EPERM，本轮**课后进度保存整体作废**（16 次，09-11~09-14，未改善）。
- **且无声**：`PROGRESS_SAVE_FAILED` 事件计数为 0（E-413 / R-22）。
- **为什么没被测出**：BUG-0001 的 10 个声明测试全绿，但**没模拟 Windows 跨句柄竞争**。
- **修复方向**：先定位竞争者（Q-051）再对齐预算；验收=连续真实课堂轮次归零。

## 3. 保护缺口（验证层面）

### R-05 矩阵跳过 `.next` —— 已实证
- **事实**：`tools/run-smoke-matrix.js` 明确 `if (entry.name === ".next") return;`；`.next` 下有 **25 个测试**，含全部 7 个 chat 路由测试与 8 个前端测试。
- **后果（实证）**：BUG-0011 的失败长期未被发现（E-304）。
- **含义**：**改 `chat/route.js` 和前端 bundle —— 这两个最高风险区域 —— 在默认验证流程里完全没有保护。**

### R-06 劫持式挂载静默失效
- **事实**：`kb-progress.js` 猴补丁 `Module._load` 包裹 `chat/route.js` 的 POST，且**一次性自我解除**（E-184）。
- **失效表现**：不报错，只表现为"进度不再受控"。
- **V-3 实测（E-406）**：运行日志中 `[kb-progress]` 出现 **198 次** → **本次实例未失效**。
- **但仍无测试断言**：只有应用跑起来看日志才能确认（矩阵跳过 `.next`）→ 建议仍做 C4 自检。

### R-16 隐式契约、失败静默
- 进度标记 `<!-- kbProgress:{} -->`、`classroom-task.json`、投影文件、`progress_state.json` 之间靠约定；`warnOnce`/`warnPageOnlyMode` 等只打日志不抛错。
- **影响**：BUG-0001 的三条机械成因全部属于此类。

## 5. 价值兑现问题（不是"债"，是"投入产出"）

### R-13 / R-20 大量能力无 UI 入口
- **量化**：7 个分支新增路由中，前端引用为 0 的有 4 个；`adaptive` 一万行默认关闭 + allowlist + 前端仅 1 处引用（E-200/E-202/E-204/E-220）。
- **含义**：分支新增约 2.4 万行生产代码，**用户能感知的只有 `practice` 与语音**。
- **对重构的提示**：不要假设"没 UI = 该删"。`math-speech` 文档与测试最完整（E-226），可能是**最接近可交付**的一块，只是差一个入口。
