# 任务描述与初始 Prompt 的写法（参考稿，最终以你的版本为准）

> 这份是给你做参考的。三个包各自的任务描述骨架 + 一份可以直接改的初始 prompt 草稿。
> 我尽量只给「结构和必须写进去的约束」，措辞你按自己的风格重写。

---

## 一、先想清楚一件事：任务描述 ≠ 初始 prompt

| | 任务描述 | 初始 prompt |
|---|---|---|
| 给谁看 | 提交表单里的裁判 / 平台运营 | 被测 agent（它只看得到这个） |
| 目的 | 证明这是 **General Agent 类** 任务，不是 coding | 让 agent 能开始干活 |
| 长度 | 3–6 句，讲**业务目标 + 交付物形态** | 可以长，但要克制；细节靠素材自己长出来 |
| 禁忌 | 别说"用 Python 写脚本分析"（会被判 coding） | 别把锚点答案、异常清单写进去（任务就废了） |

**最容易踩的坑**：任务描述里为了显得技术含量高，写"用脚本对 json 做结构解析" —— 裁判会认为
你的核心交付物是脚本。正确写法是只讲**你要什么结论**，让 agent 自己决定用什么手段。

---

## 二、任务描述的三个必写要素

1. **对象是什么**（一批教学档案 / 一套设定语料 / 32 份角色人设）
2. **要回答什么问题**（一句话，且这个问题本身有业务价值）
3. **交付物是什么形态**（报告 / 表 / 清单 / 白名单 —— 必须是文档类，不是代码）

再加一句**只读声明**就够了。不需要写"这很难""需要 100 次调用"，那是平台该判断的。

### T1 任务描述（参考）

> 某在线教学产品积累了两个学期的课堂档案，包含对话记录、概念小结、课程小结、闪卡与教材索引。
> 产品负责人怀疑归档链路有遗漏，但没有任何现成的监控。请对这批档案做一次完整的健康度审计，
> 回答三个问题：**哪些课缺了衍生内容、哪些衍生内容找不到来源、档案体积的主要构成是什么**。
> 交付一份审计报告（含覆盖矩阵表、异常清单、体积归因）与 8 条以内的整改建议。素材只读。

### T3 任务描述（参考）

> 一套游戏世界观的考据语料（253 篇）里，「时间」的表达方式并不统一：有的来源用相对纪元，
> 有的用社区重排的公元纪，有的用地区性历法。请审计这套语料在时间表述上的**自身矛盾**，
> 产出冲突清单、审计报告，以及一份"哪些时间表述可以安全写进角色设定"的白名单。
> 注意语料里已有一份成文的分级规则，你的裁定必须遵循它。素材只读。

### T4 任务描述（参考）

> 32 个角色的人设模板要接进一个苏格拉底式教学产品。产品对字段长度、人设结构、头像规格、
> 语音资源都有硬约束。请审计这 32 份素材在真实约束下的可用性，产出合规矩阵、
> 逐角色问题段落对照表、头像可用性报告，以及索引与文档的一致性发现。素材只读。

## 三、初始 prompt 的骨架（五段式）

我建议所有三个任务都用同一个骨架，只是内容不同。这样你自己维护起来也方便：

```
【第 1 段 · 场景与身份】1–2 句。你是什么角色，在什么背景下做这件事。
     ↓ 目的：让 agent 建立"我在替谁干活"，而不是"我在跑一个测试"
【第 2 段 · 素材位置】绝对路径 + 一句话说明每个子目录是什么。
     ↓ 目的：省掉它 ls 半天的无用调用（这部分不该算进 100 次里）
【第 3 段 · 要交付什么】编号列表，每项写清「文件名 + 内容 + 判定粒度」
     ↓ 目的：交付物形态一旦模糊，agent 会自由发挥，评分就没法对齐
【第 4 段 · 硬约束】只读 / 不许整读大文件 / 结论必须可溯源 / 必须遵循已有规则文件
     ↓ 目的：这是纪律段。缺了它，审计会变成改动
【第 5 段 · 完成标准】"什么时候算做完" + 输出目录
```

### 第 4 段是重点，我单独展开

这是三个任务**共通的四类约束**，建议原样保留（措辞你可以改）：

1. **只读纪律**
   > 素材是只读拷贝，任何情况下不得修改、移动、删除其中任何文件。你可以写临时脚本放在
   > 输出目录里，但不要改动素材本身。如果发现文件内容有问题，写进报告，不要修复。

2. **禁止整读**
   > 目录中有体积超过 100MB 的单个文件。不要尝试一次性读取全文；请先读结构、再按需定位、
   > 必要时抽样。读取大文件前先确认它的体积和顶层结构。

3. **溯源强制**
   > 报告中每一条结论都必须能追溯到「具体文件路径 + 位置（行号 / 消息序号 / 字段路径）」，
   > 并附原文引句。无法溯源的结论按编造处理。

4. **规则先行**（T3 必需，T1/T4 可选）
   > 素材中已有一份成文的分级/规格说明（路径见上）。**先读它，再开始判断**。
   > 你的裁定必须遵循它；当规则与直觉冲突时，以规则为准，并在报告中说明你遵循了哪一条。

> 第 4 条其实是这三个任务真正的分水岭。多数 agent 会跳过规则直接按常识判，
> 然后在「看起来像问题其实合规」的样本上翻车。你要的正是这个区分度。

## 四、三份可直接改的初始 prompt 草稿

### T1

```
你是一名数据审计员，受某在线教学产品的负责人委托，对两个真实课堂世界的档案做健康度审计。
这批档案没有任何监控，负责人怀疑归档链路有遗漏，需要你给出可核查的结论。

素材位置（只读）：
  <包路径>/world_KU/   主样本，一个使用量大的世界
  <包路径>/world_HH/   对照样本，一个使用量小的世界，目录结构完全同构
两个世界都包含：chats/（课堂对话）、concept-summaries/、lesson_summaries/、flashcards/、
conversations/、textbooks/（仅页面级元数据与索引，无 PDF 本体）、以及若干角色与世界设定文件。
先读两个目录下的 README.md 了解体量与已知说明。

请交付以下四项，全部写入 <输出目录>/：
1. 覆盖矩阵（CSV）：每节课 × {概念小结, 课程小结, 闪卡, 会话目录} 的命中情况，两个世界各一份。
2. 异常清单（Markdown 表格）：孤儿、缺件、索引漂移、体积异常、内容损坏，每条给
   路径 + 证据 + 你的判断理由。按严重度排序。
3. 体积归因报告（Markdown）：档案总体积的主要构成是什么。要求逐字段归因，不要只看文件大小。
4. 整改建议（Markdown）：不超过 8 条，写给产品负责人看，是决策建议不是代码。

硬约束：
- 素材只读。不得修改/移动/删除任何文件；发现问题写进报告，不要修复。
- 目录中存在超过 100MB 的单个文件，不要整读。先看结构与体积，再按需定位、抽样。
- 每条结论必须可溯源到「文件路径 + 位置」，附原文引句。无法溯源的按编造处理。
- KU 与 HH 结构同构，请用 HH 作为基线来判断 KU 的异常究竟是特例还是系统性问题。

完成标准：四份文件齐备，异常清单中每一条都能被独立复核。输出目录为 <输出目录>/。
```

### T3

```
你是一名设定考据审计员。一套游戏世界观语料（253 篇考据正文）在「时间」的表达上并不统一：
有的来源用相对纪元，有的用社区重排的公元纪，有的用地区性历法。请审计它的自身矛盾。

素材位置（只读）：
  <包路径>/资料/可用文本/   253 篇考据正文，按两个作品分目录
  <包路径>/资料/索引/      11 份索引与规则文件

**开始判断之前，必须先读这两份**：
  索引/提瓦特历法与时间表达.md   —— 时间表达的四层结构与可信度三档，以及写入规则
  索引/模板资料体系说明.md       —— 全局的资料性质分级规则
你的所有裁定都必须遵循这两份文件的规则。当规则与直觉冲突时以规则为准。

请交付以下三项，全部写入 <输出目录>/：
1. 冲突清单（Markdown 表格）：列 = 来源 ID / 原文引句 / 位置 / 冲突对象 / 建议裁定 / 理由。
   按「确定冲突 → 疑似冲突 → 已确认为非冲突」三档组织。
2. 审计报告（Markdown，8–12 页篇幅）：说明这套语料的时间表达分几层、
   哪一层被谁混用过、混用的具体机制是什么。
3. 可安全写入角色设定的白名单（Markdown）：按 提瓦特历法与时间表达.md 的写入规则筛选，
   每条注明它属于哪一可信度档位。

硬约束：
- 素材只读。
- grep 命中后必须回读上下文再判断。同一个词在不同语境下可能是节庆名、可能是比喻，
  也可能是真实日期；只看命中片段会大面积误报。
- 每条冲突必须给「文件相对路径 + 行号或来源编号 + 原文引句」。
- 注意：角色在对话中的**主观陈述**不是客观史料。请先确认分级规则怎么处理这类陈述，
  再决定它算不算冲突。

完成标准：三份文件齐备，冲突清单中每一条都能被独立复核。输出目录为 <输出目录>/。
```

### T4

```
你是一名内容资产审计员。32 个角色的人设素材即将接入一个苏格拉底式教学产品，
产品对字段长度、人设结构、头像规格、语音资源都有硬性约束。请审计这批素材的可用性。

素材位置（只读）：
  <包路径>/角色/               32 个角色目录，每个含 模板.md（实际使用的人设）、
                               设定.md（背景参考）、图片/；另有素材索引与文档
  <包路径>/规格/voice-catalog.json   已实装语音的清单
  <包路径>/README.md           素材说明与上游约束的摘录

请交付以下四项，全部写入 <输出目录>/：
1. 合规矩阵（CSV）：32 行 × N 列，N 至少覆盖字段长度、必需段落、性别/年龄一致性、头像可裁方形。
2. 逐角色问题段落对照表（Markdown）：只给文本层面的改法建议，不要提交代码。
3. 头像可用性报告（Markdown）：逐张判断能否裁成方形；给出需要处理的具体文件。
4. 索引与文档一致性发现（Markdown）：素材目录里的索引、说明文档与磁盘实际内容之间是否一致。
   如不一致，给出确切数字与差异项。

硬约束：
- 素材只读。
- 图片可用性必须真看图判断，不能只依赖索引文件里的声明。
- 字段长度限制请以 README 中列出的上游规格为准；超出限制才算问题，
  但**符合规范的空值不算缺失**，请先确认规范对空值的规定再判定。
- 每条结论给「角色目录 + 文件 + 段落标题」；语音相关结论给 voiceId。

完成标准：四份文件齐备，矩阵行数与磁盘实际角色数一致。输出目录为 <输出目录>/。
```

## 五、几个具体的调优点

1. **别把「对照样本」写得太明白。** T1 里我只写了"HH 是使用量小的对照"，没告诉它 HH 更干净。
   如果 agent 自己发现"HH 也有同样的缺件"，那是加分项。

2. **T4 的「空值不算缺失」这句可以更含糊一点。** 现在这句接近提示。你可以改成
   "请先确认规范对空值字段的规定" —— 保留了考察点，但不直接给答案。

3. **T3 的最后一段（主观陈述）同理。** 这是整套任务里性价比最高的一个陷阱，
   但你写太细就是送分。建议保留"请先确认分级规则怎么处理这类陈述"，删掉后面那半句。

4. **调用量不够时的补救**：如果实测不到 100 次，最有效的加码不是加大素材，而是**加交付物粒度**：
   - T1 加一列"每节课的教学主题标签"（要真读对话才能标）；
   - T3 加一份"逐篇来源的时间表达摘录表"（253 行，每行都要读）；
   - T4 加一份"32 个角色的性格关键词提取 + 与 voice-catalog 的性别/气质匹配度"。

5. **不要写"请展示你的思考过程"。** 这类要求会让 agent 把 token 花在叙述上而不是工具调用上，
   反而压低调用量。

6. **输出目录必须给绝对路径。** 否则 agent 会写在素材目录里，违反只读。
